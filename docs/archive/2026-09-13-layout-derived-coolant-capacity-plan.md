# 固定实验堆布局派生冷却剂容量整改计划

**状态：** 已完成并归档；`P1-COOL-06` 于 2026-09-14 通过用户客户端验收、项目经理自动复验和 Git 集成

**确认日期：** 2026-09-13

**适用版本：** Minecraft 1.21.1、Java 21、NeoForge 21.1.219、Create 6.0.10-280

**实施入口：** [P1 单步执行计划中的 P1-COOL-06](2026-08-18-agent-developer-execution-plan.md#p1-cool-06按堆芯空置空间派生共享冷却剂容量)

## 1. 问题与目标

当前实现把每座反应堆的冷态和热态库存分别固定为 `1000 mB`，因此任何合法堆芯布局都显示并使用 `2000 mB` 总容量。这个实现与玩家已经确认的玩法不符：燃料棒占据的内部格不能容纳冷却剂，空列和控制棒列内部保持的空气才构成反应堆冷却剂空间。

本次整改只修正固定 `5×5×5` 实验堆的容量来源、共享库存约束、信息显示和回归测试。它不实现可变尺寸反应堆、热惯性、事故世界效果、锅炉、汽轮机、Ponder 扩写或 HTML 模拟器同步。

## 2. 已确认玩法合同

### 2.1 可计容积

服务端必须从最近一次有效结构扫描已经生成的 `ColumnMapping` 派生容量：

```text
coolantSpaceBlockCount = Σ bodyPositions.size
  where column.type is EMPTY or CONTROL_ROD

coolantCapacityMb =
  coolantSpaceBlockCount × coolantCapacityPerEmptyBlockMb
```

- `EMPTY` 空列的三格内部空气全部计入。
- `CONTROL_ROD` 控制棒列在方块结构上同样是三格内部空气，全部计入；驱动器渲染的无碰撞控制棒模型和当前插入深度都不改变容量。
- `FUEL` 燃料列的三格 `reactor_fuel_rod` 不计入。
- 顶盖、换料端口、控制棒驱动器、外壳、观察窗、侧面冷/热端口和仪表端口都不计入。
- 容量只从服务端有效结构缓存和服务器配置派生。正常 tick、护目镜观察和客户端同步不得重新扫描整座结构，也不得由客户端自行推算。

P1 的固定内部高度为 3。默认 `coolantCapacityPerEmptyBlockMb = 1000` 时，必要回归锚点为：

| `3×3` 堆芯平面 | 可计空气格 | 共享容量 |
| :--- | ---: | ---: |
| 周围 8 个燃料列 + 中心 1 个空列 | 3 | `3000 mB` |
| 三行 `F-C-F`，共 6 个燃料列 + 3 个控制棒列 | 9 | `9000 mB` |
| 9 个燃料列 | 0 | `0 mB` |
| 1 个燃料列 + 其余 8 列为空列或控制棒列 | 24 | `24000 mB` |

全燃料布局仍可合法成型，但容量为零、冷端拒绝输入，属于玩家主动选择的高风险布局。结构合法性不因容量为零而改变。

### 2.2 单一共享库存

冷态 `compound_coolant` 与热态 `hot_compound_coolant` 是同一物理冷却剂的两个状态，共用一个布局派生容量：

```text
coldCoolantMb >= 0
hotCoolantMb >= 0
coldCoolantMb + hotCoolantMb <= coolantCapacityMb
```

- 冷端实际注入量同时受该端口当 tick 配额和 `max(0, capacity - cold - hot)` 限制。
- 热端只排出热态库存，实际排出量同时受热库存和该端口当 tick 配额限制。
- 冷态转化为热态不增加总体积，因此不再受独立“热缓冲剩余空间”限制；转化量受可用冷态库存、可吸收热量和既有整数 `mB` 量化规则限制。
- 热端堵塞时，已有冷态库存仍可逐步转为热态；当共享库存全部变成热态且无法排出后，因为没有冷态库存可继续吸热，冷却自然停止并进入既有损伤流程。
- 冷转热、外部输入和外部输出必须满足：

```text
nextCold = previousCold + acceptedColdIn - converted
nextHot  = previousHot + converted - actualHotOut
nextTotal = previousTotal + acceptedColdIn - actualHotOut
```

增加冷端或热端只增加吞吐量，不增加共享容量。每个物理端口默认 `128 mB/t`、无全堆流量上限的既有合同保持不变。

### 2.3 配置与兼容

- 新的服务端配置项为 `reactor.coolantCapacityPerEmptyBlockMb`，默认 `1000 mB`，允许 `0`，上限必须保证固定 P1 最大 24 个可计空气格的乘积可由 NeoForge `IFluidHandler` 的整数容量安全表示。
- 旧的 `coldInventoryCapacityMb` 与 `hotInventoryCapacityMb` 不再是权威配置，不得继续参与容量、输入、转化、摘要或显示。已有配置文件中的旧键可以由配置系统清理或保留为无效旧项，但不能继续生效。
- 冷态和热态库存数值继续由仪表端口现有 `ReactorSnapshot` 持久化；派生容量不写入快照，不为本次整改增加快照 NBT 字段或版本。
- 配置重载或结构重新成型后，下一次服务端容量读取使用新值，无需为了容量变化执行正常 tick 全结构扫描。
- 若旧存档、开发数据或配置缩小使 `cold + hot > derivedCapacity`，不得静默截断、删除或改写已有流体。此时冷端拒绝所有新输入，冷转热仍可按体积守恒执行，热端仍可排出；总量降至派生容量以内后自动恢复正常输入。
- capability 的 `getTankCapacity` 和护目镜均报告当前布局与配置得到的物理容量；超容量状态允许当前存量高于报告容量，并必须在护目镜中清楚显示，不能把容量伪增大到当前存量。

## 3. 信息显示合同

仪表端口静态摘要从有效结构缓存提供：

- 燃料列、控制棒列、空列和冷/热端口数量；
- 可计冷却剂空气格数量；
- 每格配置容量；
- 布局派生的单一共享总容量。

动态护目镜显示冷态量、热态量以及 `冷态 + 热态 / 共享容量`。不得继续分别显示两个看似独立的满容量，也不得把端口数量计入容量。摘要同步 NBT 可以为此调整字段和版本边界，但它只是临时服务端到客户端显示数据，不能成为第二份持久化权威状态。

`P1-PONDER-02` 已验收的 Java 场景保持冻结。本次只允许在语言文件中纠正现有第 4、7、8 段里“两个配置容量之和”或“独立冷热缓冲”的过时文字，使其描述布局派生共享容量；不增加步骤、不重播或扩展场景。

## 4. 实施与验收顺序

1. `P1-COOL-06` 先实现纯容量派生模型、共享账本语义、capability、服务端 tick、摘要/护目镜和配置。

3. 项目经理审查允许写集、守恒、旧状态恢复路径和测试证据，独立复验后决定是否提交。
4. `P1-VERIFY-02` 在 `P1-COOL-06` 通过前保持阻塞；解除后把 `3000 mB` 与 `9000 mB` 两种布局、共享冷/热占用和每格配置重载纳入总验收。
5. `P1-VERIFY-03` 仍在 `P1-VERIFY-02` 之后执行。

## 5. 风险控制

- 最容易出现的守恒错误是只把冷端 fill 改为共享上限，却继续用独立热容量限制冷转热，导致装满冷液的反应堆无法产生热液。验收必须覆盖“共享库存全满且全部为冷态时仍可等体积转化”。
- 容量必须复用结构扫描缓存。若为了获得空气格数量在每个 capability 调用、tick 或护目镜读取中扫描世界，本任务失败。
- 旧状态超容量必须可通过“先转为热态、再从热端排出”恢复。直接 clamp 会违反流体守恒。
- P1 固定结构最多 24 个可计空气格；配置范围、乘法和 `IFluidHandler` 的 `int` 边界必须一起测试，不能依赖整数溢出后的负数或截断。
- 当前开发存档不承诺稳定兼容，但本次可以无损保留已有冷/热库存，因此没有理由主动删除玩家流体。
