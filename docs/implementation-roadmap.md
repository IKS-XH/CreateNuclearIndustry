### 1.1 当前 P1 实施边界

用户已将当前 P1 收窄为固定 `5×5×5` 实验反应堆核心切片：反应堆可运行、正常停堆、控制棒拖动交互、燃料列降频、直接相邻燃料超频、逐列热负荷损伤与发热/燃耗反馈、失效传播/融毁倒计时、控制棒列卡死、受损燃料列维修、破坏性重组成型、红石 SCRAM 和复合冷却剂冷/热状态转化。所有玩家使用相同交互，不加入权限、身份或所有权差异。

## 3. 阶段与出口

### P0：项目合同与技术可行性

目标：让文档、版本、Create API 和验证口径一致。

出口条件：

- 五份核心文档的链接和职责明确；活动计划存在；归档规则可查；
- NeoForge、Create、Java 版本以构建文件为准并有一次 API 核查记录；
- 明确当前 P1 所需的流体能力、多端口汇总、动力机械臂、护目镜信息、拖动滑块、右键维修、方块实体 NBT 和运行中拆块拦截 API；`BoilerHeater` 与应力输出只记录后续阶段接口，不阻塞当前 P1；
- 明确当前用户工作区修改和 Git 交接规则。

**当前状态：** P0 API 探针、数值原型、GameTest 和人工验收已通过；P1 可以按活动交接计划开始执行。

### P1.0：全内容 Ponder 教学基线（G0）

目标：在每个可玩内容进入对应阶段时同步提供可操作的 Create 风格 Ponder，不把教程推迟到发布前再补。

范围：全部多方块结构、单方块设备、管道/阀门/端口和主动使用物品；纯材料只在配方/设备场景中展示。当前只交付固定实验堆核心及其冷却剂/控制交互场景，锅炉、汽轮机、生产线等场景随后续阶段完成。

出口条件：

- `content-catalog.md` 的 Ponder 矩阵中每个 ID 都有独立入口，允许复用场景但不允许遗漏触发物；
- 每个场景至少演示用途、正确搭建/放置、输入输出或交互、Create 自动化和一个故障/安全行为；
- 场景只使用已批准的注册项、配方和流体，且中英文文本可本地化；
- Ponder 只运行客户端教学动画，不拥有或修改服务端燃耗、损伤、SCRAM、换料和辐射状态；
- 每个当前 P1 核心入口完成一次客户端人工验收，资源契约能够发现缺少场景或失效触发物；后续内容按自身阶段验收。

### P1.1：内容身份与资源合同（G1）

目标：先建立反应堆运行所需的稳定身份，不宣称生产线完成。

范围：`fresh_fuel_assembly`、`cooled_spent_fuel_assembly`、`fuel_assembly` 数据组件、`compound_coolant`、`hot_compound_coolant` 以及必要的语言、创造栏、标签和资源契约；`hot_spent_fuel_assembly` 只记录未来命名预留，不纳入首发注册。

出口条件：

- 燃料组件耐久字段、燃料身份、`decayHeatHu` 预留字段和格式版本可保存/读取；
- 燃料组件不保存温度或完整度；温度属于反应堆燃料列状态；
- 燃料耗尽终态明确为 `cooled_spent_fuel_assembly`；首发运行不生成或依赖热态乏燃料；
- 占位图标不能成为煤炭、木炭、熔岩或水的运行时别名；
- 资源契约覆盖注册、翻译、模型/纹理、标签和存档往返。

### P1.2：纯模拟核心与实验反应堆（G2/G3）

目标：在不依赖 Minecraft 世界扫描和 Create API 的纯 Java 模型中冻结逐列燃耗、局部控制和反馈算法，再接入固定尺寸实验反应堆。

范围：固定 `5×5×5` 结构、四向邻接、平均控制棒深度、燃料列降频、直接相邻燃料反馈超频、燃耗/温度/余热/逐列热负荷损伤与发热燃耗反馈/失效传播、控制棒列完整度与卡死、20% 融毁触发、复合冷却剂冷/热转化、固定结构扫描缓存、仪表接口状态所有权、控制棒驱动器、红石 SCRAM、逐列换料端口和停机重组成型重置。

出口条件：

- 模拟计算确定性、有限、有界，并覆盖文档列出的正向与负向用例；
- `reactor_instrument_port` 是唯一权威状态所有者、全部反应堆运行 NBT 的持久化核心和唯一外部 SCRAM 红石输入端；`reactor_control_port` 不参与 P1，后续可选且不拥有状态；
- 不注册独立 `reactor_interlock` 方块；任何外部安全逻辑、管理员或 Create 红石线路都必须向 `reactor_instrument_port` 输入信号触发 SCRAM；
- `control_rod_drive` 不接受红石调节；所有玩家通过逐棒拖动滑块修改目标深度，烈焰人管理员服务端控制桥接后置；
- `reactor_instrument_port` 仅在结构中至少存在一个控制棒列时接受高电平 SCRAM，插入所有仍可移动的控制棒并锁定滑块；无控制棒列时拒绝请求、不建立 SCRAM 状态且不能暂停融毁倒计时；有棒时保留高电平请求，插棒后仍有裂变产热则报告不完整停堆；低电平解除已建立的 SCRAM 后恢复高电平前保存的停堆目标位置；
- 结构只在结构变化时扫描，正常运行不逐方块扫描；
- 所有玩家用 Create 扳手普通右键 `reactor_instrument_port` 时可请求一次服务端权威重扫，并通过本地化快捷栏消息看到成型成功及列/端口计数，或确定性的未成型原因；诊断不得改写运行快照、启动模拟或要求客户端扫描结构；
- 换料端口无 GUI，只接受人工或 Create 动力机械臂，且服务端原子校验；
- 佩戴工程师护目镜指向燃料列顶部换料端口时，能读取并显示该列燃料组件剩余耐久、列完整度/损坏度和当前 `HU/t` 发热量；显示复用结构缓存，不触发整堆扫描；
- 端口不能复制、补满、删除燃料组件状态；
- 冷却剂转化按可用发热、冷端实际输入汇总、热端实际接收容量汇总、内部库存/背压和每单位冷却剂吸热量的最小值结算；P1 允许多个冷端/热端汇总流量，每个端口默认上限为 `128 mB/t`，不设置全堆流量上限，重复端口或连接不得重复结算；
- 每个燃料列在多方块结构服务端状态中独立持久化 `fuelColumnIntegrity`，每个控制棒列另有 `controlRodColumnIntegrity`；完整度下降只由燃料列累计有效热负荷结算，超频仅提高发热，不是独立损伤源；冷却足以带走该列热量时超频不降低完整度；
- 完整度越低，列发热和燃耗按相同比例增加，完整度归零时反馈倍率封顶为 2.0；归零本身不停止发热、燃耗或四向传播，只要组件尚有耐久且未被控制棒压至零裂变功率就继续运行。组件耗尽后才停止该列裂变发热、燃耗和失效传播；目标列冷却足够时阻断传播。控制棒列归零后卡死但不传播；当前传播热量覆盖默认 20% 有效燃料列时进入持久化 `meltdownCountdown`，SCRAM/冷却可以暂停但不能回退进度；
- 受损燃料列可以用 1 块 `steel_plate`（显示名“合金钢板”）右键换料端口修复，每次恢复 `0.25 / internalHeight` 且目标列必须停止放热；控制棒列用同一物品右键 `control_rod_drive` 修复；完全停机且余热进入安全区后重组成型会永久清空结构全部内部 NBT，运行/倒计时/暂停期间拆件直接执行融毁动作；
- NeoForge GameTest 覆盖结构识别、唯一仪表接口、控制棒同步和换料拒绝原因。

### 后续首发扩展 A：生存生产线（原 P1.3/G4）

目标：从原版与 Create 材料出发，完成实验堆所需的最小可达生产链。

范围：铅/锡/铀矿物及标签、基础工业材料、复合冷却剂、铀富集、芯块烧结、燃料棒/组件、一级管道、屏蔽装配、封存路线。

出口条件：

- 每条首发配方都有真实游戏内来源、标签输入和自动化入口；
- 数量/时间/转速/应力等未冻结前，只验收依赖和守恒，不声称平衡完成；
- 铀尾矿、冷却剂容器、乏燃料和其他副产物没有无声删除；
- 无第三方材料模组时仍可走通首发链；
- 数据生成、资源契约和至少一条生存流程人工验收通过。

### 后续首发扩展 B：热端与动力闭环（原 P1.4/G5）

目标：完成“热复合冷却剂 → 高压锅炉 → 超临界蒸汽 → 汽轮机 SU → 普通蒸汽 → 核换热器冷凝水”的首发闭环。

范围：三模式核换热器、专用高压锅炉、超临界汽轮机、普通 `steam`、多主轴输出、耐压管网和基本仪表。

前置：先完成 P0 的 Create API 可行性证明，再冻结热源品质和流体账本。

出口条件：

- 只有 `NUCLEAR_SUPERCRITICAL` 能产生超临界蒸汽；普通热不能通过叠加升级；
- 超临界汽轮机排出同一个普通 `steam`，不会重复结算应力；
- 冷凝模式无冷源或出水受阻时安全停机且不吞入蒸汽；
- 负载切断、供水不足、冷却不足、排汽堵塞和换热器空载有不同原因与处置；
- 多主轴输出不会重复注册总应力；
- GameTest、纯模拟测试和一次完整游戏内手动验收均通过。

### P2：自动化与可变规模

在当前 P1 核心和后续首发扩展的接口稳定后实现可变尺寸反应堆、分段汽轮机、显示链接、比较器、仪表端口红石安全线路和烈焰人管理员。P2 不得反向改变 P1 已冻结的注册身份和核心状态语义。

### P3：风险与长期闭环

实现辐射、防护、污染、乏燃料再处理、再生燃料、维护和管道等级。首发不注册受污染复合冷却剂、冷却剂净化器或相关过滤产物。任何 P3 内容都不能成为首发可玩切片的前置依赖。

### P4：教程、彩蛋、性能和发布评估

在运行事件稳定后实现彩蛋/进度、Ponder 高级教程与演出打磨、音效动画、性能压力测试、许可证和发布准备。P1/P2/P3 内容的基础 Ponder 不得拖到 P4；彩蛋关闭时不得改变主线。

  ├─→ P1.0 Ponder 框架与内容覆盖合同
  │     └─→ 随 P1 核心、后续首发扩展、P2/P3 内容逐项交付场景

  │     └─→ P1.2 纯模拟核心

  └─→ 后续首发扩展 A：最小生存生产线
        └─→ 后续首发扩展 B：换热器、锅炉、汽轮机与 SU 闭环

P1.1 和 P1.2 构成当前 P1 核心关键路径；后续首发扩展可以提前做接口设计，但开发者不得以“创造模式可获得”代替生存生产线完成，也不得在 Create 热源/应力 API 尚未证明前实现热端闭环。

## 5. 不可绕过的验收门

1. **身份门：** 注册 ID、数据组件和流体状态先于运行逻辑；改名必须经过项目经理和用户确认。
2. **模拟门：** 核心公式有纯单元测试，不能只靠进游戏观察数值。
3. **资源门：** 每个内容项具备注册、翻译、模型/纹理、掉落/标签、来源和测试证据。
4. **守恒门：** 流体、燃料、热量、应力和危险废物不得复制或无声删除。
5. **服务器门：** 运行状态、燃耗、损伤和交互由服务端权威验证；客户端只做显示和动画。
6. **性能门：** 结构和管网使用缓存；非活动区块不做完整模拟；事故世界修改限流。
7. **生存门：** 从原版/Create 材料能实际完成生产、启动、运行、停机和安全封存。
8. **Ponder 门：** 每个多方块结构、单方块设备、管道/阀门/端口和主动使用物品都有独立入口；入口内容与配方/运行合同一致，并通过客户端人工验收。
9. **交接门：** 开发者提供改动清单、验证命令、失败用例、游戏内结果、未完成项和下一依赖。

当前“资源门”只要求占位资源引用完整、方块和物品在客户端可识别且不出现缺失模型；连接纹理、正式多边形模型、Flywheel 动画、粒子、音效和最终美术统一均暂缓到功能闭环之后。功能任务不得顺带修改这批正式视觉资源。

## 6. 当前阻塞与待决策项

- 当前 P1 固定为 `5×5×5` 实验反应堆核心；可变面积和高度后置，不再是当前尺寸阻塞项。
- 核换热器首发默认值已确定为核热 18、普通蒸汽供热 9；两个值进入服务器配置文件，可由后续平衡或整合包覆盖，热端实现仍属于 P1 之后。
- `contaminated_water` 确认保留为独立核废水/污染线；删除范围仍只包括受污染复合冷却剂、净化器和过滤产物。
