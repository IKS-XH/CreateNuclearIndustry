## 1. 角色与职责

| 事项 | 用户 | 项目经理 | Agent / 开发者 |
| :--- | :--- | :--- | :--- |
| 玩法、平衡、技术路线与范围 | 提出需求并决定未决取舍 | 共同讨论、核查依据、分析成本和可行性、记录结论 | 提供实现证据和建议，不自行改变设计 |
| 核心文档与活动计划 | 可直接修改 | 维护受影响文档、依赖、任务卡与版本记录 | 只读；在指定报告中提出修订建议 |
| 代码、测试与功能资源 | 决定需求和验收目标 | 只读审查、安排验证、反馈问题，不代写实现 | 按已确认任务卡实施、测试并报告 |
| 验收与进度 | 完成或确认需要的人工体验验收 | 审核差异与证据、必要时独立复验、更新任务状态 | 提交实际结果，不自行宣布阶段通过 |
| Git 与工作区集成 | 可执行版本操作 | 负责提交、回退、分支、合并及冲突处理编排 | 只读检查，交付未提交改动 |

项目经理不编写或修改功能代码、测试代码、构建脚本、模拟器或自动化程序；发现问题时形成可执行的任务或整改要求。项目经理可以阅读代码和依赖、运行已有构建与测试命令、检查日志及管理文档。代码或资源冲突由执行者在指定文件范围修复，文档冲突由项目经理处理，Git 合并的继续或中止仍由项目经理执行。

项目经理负责工作区内属于本项目的主策划、设计修订、内容清单、配方关系、路线图、活动计划、README、工具说明、索引、验收归档和版本说明。核心文档与活动计划只允许用户和项目经理修改；执行者只有在任务卡明确列入允许路径时，才可更新交付报告或工具说明。历史报告保留原验收语境，不通过改写历史记录追认新需求；与本项目无关的工作区文件不纳入管理性清理。

### 1.1 项目经理授权判定

1. 只有用户在对话中针对某个具体角色作出的明确任命才产生项目经理权限。用户未作此任命时，无论执行者使用何种模型、工具、名称或对话入口，都必须按执行者权限行事。

3. 角色信息缺失、互相冲突或无法确认时，相关角色仍是执行者。执行者应停止拟进行的治理、验收、派发和 Git 写操作，并在交付报告中说明歧义，等待用户或现任项目经理处理。
4. 执行者可以报告完成情况、验证证据、风险和建议，但不得以项目经理身份修改 `AGENTS.md`、核心文档或活动计划，不得改变任务状态、接受或拒绝交付、派发或指挥其他执行者，也不得执行 Git 写操作。报告中的“完成”只表示执行者已交付，最终验收状态由项目经理记录。
5. 只有用户可以任命、更换或撤销项目经理。用户作出新任命后，获任命者应更新治理入口和活动计划；在文档同步完成前，用户的最新明确任命仍具有最高效力。

## 2. 需求讨论与落文档

1. 项目经理先说明玩家要解决的问题、预期交互、输入输出、失败与恢复方式，以及对平衡、性能、兼容和工期的影响；技术结论区分已验证事实、设计推断和待验证假设。
2. 用户已经明确提出并确认的需求直接整理入文档；同一授权不重复询问。仍有互斥玩法、重大范围或兼容性取舍时，先提出具体选项与依据，保留未决状态。
3. 讨论和评审建议不自动成为已批准需求。对整份评价的认可不等于逐项批准其中的玩法修改；未经确认的建议可登记为待讨论事项，不能写成已冻结合同或派发编码。
4. 确认后只同步实际受影响的文档，并记录日期、需求来源、结论、替代的旧规则、受影响任务和验证要求。涉及 Java、HTML 模拟器和配置的共同规则，任务计划必须列出需要同步的实现和对照验证。
5. 文档冲突先停止受影响任务的派发或执行，由项目经理整理冲突及影响，再按用户已确认的规则协调；需要新取舍时由用户决定。无关且依赖已满足的工作可以继续。

**设备交互风格（2026-10-02用户明确要求）：** 本模组所有设备保持Create式无独立设备GUI交互，不再新增右键库存/控制面板。设备状态通过世界内表现、工程师护目镜等原生方式显示；配置优先采用Create原生过滤槽、数值行为和扳手，物料在世界内手动操作或由物流设备搬运。原生过滤/数值控件不等同于自制设备GUI。本轮先移除离心机菜单；后续任务与验收必须遵守本规则，历史界面报告保留当时语境。

需求状态使用“待讨论、已确认、待验证、已取代”；任务状态使用“待派发、执行中、待验收、需整改、已完成、阻塞”。已确认的玩法仍可因技术假设未验证而暂不可派发，两种状态不能混为一谈。

**配方工序选择（2026-10-03用户明确要求）：** 后续除确实需要大批量生产的基础零件外，默认不使用序列装配，尤其不为单一功能零件叠加装配步骤。优先选择工作台、动力合成或单步Create原生加工。任务设计如采用序列装配，须说明量产需求及多步工序的必要性；不能仅为提高复杂度设置半成品。现有已验收配方不自动改动，后续涉及时逐项调整。具体规则同步于[配方表](./recipes.md#22-标签与替代材料)。

**工作台类型（2026-10-06用户明确要求）：** 设备和零件的工作台配方使用有序合成，避免Create搅拌机自动把制造配方转换为无序加工；粗矿块和金属锭拆解保持无序。只调整格子布局，原料标签/item身份、重复数量、产量及注册ID保持不变。明确设计的混粉、合金或流体搅拌继续采用Create原生加工类型，不改变第三方配方及Create全局自动转换配置。现有13条设备配方按[整改卡](archive/2026-10-08-completed-plans/2026-10-06-crafting-shaped-01.md)执行。

## 5. 交付与验收

执行者提交未提交改动和指定路径中的报告，列出任务 ID、基准提交、实际技能入口、修改文件、行为变化、验证命令与结果、人工验收、兼容影响、未实现项及下一依赖。报告中的“提交”指交付报告，不授予执行 Git commit 的权限。

项目经理核对文件范围、中文注释、行为与文档一致性，再审查测试证据，必要时运行已有命令独立复验。逻辑验证、真实 Create 管网 / 机械臂集成、客户端操作体验与多人行为各自提供相应证据，单元测试或构建成功不能替代其他验收。历史报告必须标出时间和基线，不能冒充本次运行结果。

通过后由项目经理更新活动计划和路线图、处理归档并完成适用的版本操作；未通过则形成明确整改项交回执行者，项目经理不代写修复。纯文档变更核对差异范围、链接、术语和一致性，并执行 `git diff --check`；无运行行为变化时不额外跑 Minecraft 测试。

| 改动范围 | 默认必要检查 | 扩大验证的条件 |

| 自有设备、库存、持久化、流体或计算逻辑 | 受影响的单元测试及必要真实机器用例，覆盖守恒、恢复或兼容等本次关键不变量 | 影响公共状态模型、共享事务/生命周期或跨模块调用时扩大相关回归 |

执行约定：

## 6. Git 与工作区管理

- 只有用户和项目经理可以执行 Git 写操作。执行者禁止 `add`、`commit`、`reset`、`restore`、`revert`、`checkout`、`switch`、分支创建/修改、`merge`、`rebase`、`cherry-pick`、`stash`、`clean`、标签创建/修改和 `push`，也不得直接修改 `.git`、通过 GUI 或脚本绕过该规则。只读的 `status`、`diff`、`log`、`show` 和版本查询可用于报告。
- 项目经理在操作前检查当前分支、基准提交、暂存区、未提交改动和执行者活动范围。只暂存本次已经审核的文件或片段，不使用 `git add .` 夹带日志、存档、生成物或其他任务改动。
- 新建工作分支默认使用 `codex/` 前缀；保留已有分支语义。提交按可追踪的任务或文档变更组织，提交信息使用中文，必要任务 ID 和技术标识保持原文。
- 回退优先使用可追踪的 `git revert`；回退前确认目标提交、受影响任务与用户已有改动，不用 `reset --hard`、强制检出或清理命令掩盖失败。尚未授权且会丢弃用户工作或改写已共享历史的操作，必须先向用户说明具体影响并取得授权；已授权范围不重复询问。
- 合并前确认来源与目标分支、相关测试和文档状态，并使用适合该合并的干净工作区。存在无关未提交改动时保留它们，选择隔离工作区或推迟合并，不擅自删除或收纳用户工作。代码冲突交执行者处理，项目经理审核后继续或中止 Git 流程。
- 项目经理维护版本说明、兼容影响与已知限制；发布制品和远端推送遵循用户已经确认的范围与仓库发布方式，不因本协议自动新增发布平台、流水线或公开版本。
- 文件权限或执行环境阻止 Git 写入时，保留已完成文档和代码，报告具体阻塞及尚未执行的版本操作，不绕过权限、不宣称提交成功。职责授权与工具是否具备写入能力分别记录。
