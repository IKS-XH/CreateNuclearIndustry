# 交给 Agent/开发者的可执行开发计划：P1 实验反应堆

**计划状态：** 待执行
**计划维护者：** 项目经理（Codex）
**需求决策人：** 用户
**执行者：** 经项目经理分派的 Agent 或开发者
**适用版本：** NeoForge 1.21.1、Java 21、Create 6.0.10、Ponder 1.0.82
**当前源码基线：** 只有 `experimental_reactor_casing` 外壳样例，反应堆核心逻辑尚未实现

本文件是实现交接单，不是玩法设计文档。设计语义以仓库中的核心文档为准；执行者不能通过修改设计文档来改变任务含义。

## 1. 必须使用的 Minecraft 开发技能

执行本计划必须使用已经安装的以下技能，并遵循其 API、目录和验证约定：

1. `minecraft-modding`：NeoForge 1.21.x 注册、方块实体、网络同步、客户端交互、数据生成、Create/Ponder 集成和资源组织。
2. `minecraft-testing`：JUnit 5 纯逻辑测试、NeoForge GameTest、测试结构模板、服务端集成测试和测试证据。

开始编码前必须重新读取这两个技能的 `SKILL.md`，并以 `gradle.properties`、`build.gradle` 和实际依赖版本确认平台。不得将 Forge 1.20.1、Fabric 或旧版 Create API 的示例直接复制到本项目。

实现时遵守以下平台边界：

- 注册使用 NeoForge 1.21.1 对应的 `DeferredRegister`/事件总线模式。
- 反应堆模拟、NBT 写入、红石判断、流体守恒和物品事务全部在逻辑服务端执行。
- Create 风格滑块、护目镜显示和 Ponder 只负责客户端表现；客户端输入必须通过服务端验证后改变状态。
- 每个注册方块、物品、方块实体、配方和教学入口都必须同时补齐对应资源和测试。
- 优先使用数据生成；若手写 JSON，必须提供资源契约测试。

## 3. 开工前只读检查

执行者接单后按顺序完成以下检查，不得修改文件：

1. 读取本计划和全部核心文档。
2. 执行 `git status --short --branch`，记录当前分支和是否存在用户修改。
3. 执行 `git diff --name-only`，确认不覆盖既有未提交文件。
4. 读取 `gradle.properties`、`build.gradle`、`settings.gradle`，确认 NeoForge、Minecraft、Create、Ponder 和 Java 版本。
5. 执行一次 `./gradlew test` 或 Windows 下的 `.\gradlew.bat test`，记录基线结果。
6. 若基线无法通过，先报告失败日志；不得把基线修复混入当前功能任务，除非项目经理单独授权。

## 4. 实施顺序和任务合同

任务必须按依赖顺序交付。后一个任务不得用未完成任务的临时实现冒充完成。

### P0-API-01：Create/NeoForge API 探针

**目标：** 以最小实验确认 P1 依赖的真实 API 入口。

**范围：** `src/test/`、必要的临时探针代码和经批准的测试配置；探针不得改变正式玩法注册。

**必须验证：**

- 普通冷却剂/热冷却剂能力和多冷端、多热端汇总方式。
- Create 风格浮动滑块的客户端输入、服务端同步和拖动结束提交。
- 工程师护目镜对目标方块的只读信息显示入口。
- Create 动力机械臂访问换料端口的事务边界。
- 换料端口右键使用 `alloy_steel_plate` 的服务端交互入口。
- 运行中方块拆除拦截、结构破坏事件和融毁动作触发点。
- 方块实体 NBT 保存、加载、客户端同步和存档重载。

**不在范围：** `BoilerHeater`、Create 应力输出、汽轮机等后续阶段 API。

**出口：** 每项给出可用 API、调用侧、线程侧、失败行为和最小验证代码；若 API 不可行，必须在进入 P1 实现前回报替代路线。

### P1.1-DATA-01：注册、配置和数据合同

**目标：** 建立 P1 所需注册 ID、服务器配置和数据生成骨架。

**范围：** 注册类、配置类、物品/方块/流体/方块实体的资源、配方、标签、语言和资源契约测试。

**必须覆盖：** 固定 5×5×5 实验反应堆所需的核心、外壳、仪表端口、冷/热端口、换料端口、控制棒驱动器、燃料组件、工程师护目镜、合金钢板和冷却剂 ID。

**规则：** 不注册已经删除的冷却剂净化器、受污染冷却剂路线、工业仪表或独立 SCRAM 联锁器。SCRAM 的唯一外部红石入口是 `reactor_instrument_port`。

**配置原型：** 以下值必须进入服务器配置，维修消耗和维修恢复量除外：

| 配置项 | P1 原型默认值 |
| :--- | :--- |
| 单燃料列基础发热 | `1.0 HU/t` |
| 单燃料块燃烧时间 | `3 h`；与基础燃耗字段二选一 |
| 冷却剂吸热量 | `1.0 HU/mB` |
| 单端口最大流量 | `100 mB/t` |
| 反应堆总流量上限 | `200 mB/t` |
| 损伤起算有效热负荷 | `0.25 HU/t` |
| 完整度损伤速率 | `0.00125 / (tick·HU/t)` |
| 热量传播系数 | `0.25`，燃料列和控制棒列相同 |
| 融毁触发覆盖比例 | `20%` 有效燃料列 |
| 融毁倒计时 | `900 ticks` |

**固定维修规则：** 每次消耗 1 个 `alloy_steel_plate`；目标燃料列必须停止放热；恢复值为 `0.25 / internalHeight`；控制棒列使用同一物品右键 `control_rod_drive`。这些维修消耗和恢复量不得由配置覆盖。

### P1.2-SIM-01：服务端逐列反应堆模拟

**目标：** 实现可独立测试的确定性热量、燃耗、控制棒、完整度和融毁状态机。

**范围：** 模拟纯逻辑、配置读取、序列化数据结构和 JUnit 测试。

**必须实现：**

- 每个燃料列独立保存燃料组件状态、缓存热量、`fuelColumnIntegrity`。
- 每个控制棒列独立保存 `controlRodColumnIntegrity`、目标深度、实际深度和卡死状态。
- 完整度越低，发热和燃耗按相同比例增加；推荐乘数为 `2 - integrity`。
- 燃料列完整度归零后停止发热和燃耗，但其缓存/衰减余热仍可现场传播。
- 损伤只由有效热负荷产生；冷却足够时超频不会降低完整度。
- 热量只沿水平四向相邻传播；不创建传播标记、传播历史或损伤包。
- 目标列冷却足够时阻断传播；燃料列和控制棒列使用相同传播速度/系数。
- 控制棒列完整度归零后卡死，不再向外传播，但保留实际插入比例对相邻燃料列的抑制。
- 当前传播热量覆盖 20% 有效燃料列时建立持久化融毁倒计时；控制棒列不计入分母。
- SCRAM/有效冷却只能暂停倒计时，不能回退；所有燃料列和控制棒列恢复完整后才清零融毁状态。

**测试：** JUnit 覆盖边界值、逐列独立性、快照顺序无关、冷却阻断、归零行为、控制棒卡死、倒计时单调性和 NBT 往返。

### P1.2-COOLANT-01：多端口冷却剂账本

**目标：** 在服务端实现冷却剂输入、发热转换和热冷却剂输出守恒。

**必须实现：**

- 允许多个冷却剂输入端口和输出端口。
- 每个端口受单端口流量上限约束，反应堆总流量受总上限约束。
- 实际转化量取可用发热、实际冷却剂输入、热端输出容量和吸热量换算的最小值。
- 输入堵塞、输出堵塞或无冷却剂时不得复制、吞掉或凭空减少燃料消耗。
- 端口数量不得直接增加发热或燃料消耗。

**测试：** JUnit 覆盖账本守恒；GameTest 覆盖多端口汇总、重复连接、流量上限、输入/输出阻塞和存档重载。

### P1.2-REACTOR-01：5×5×5 反应堆核心和控制

**目标：** 将结构扫描、仪表接口权威状态、控制棒交互、SCRAM 和冷却剂端口接入服务端模拟。

**必须实现：**

- 仅实现固定 5×5×5；可变面积和高度不进入本阶段。
- 所有反应堆运行时 NBT 统一保存在唯一的 `reactor_instrument_port` 方块实体中。
- 初次成型和完全停机后重组成型时，所有控制棒默认完全插入。
- 所有玩家均可拖动 Create 风格滑块；不加入权限、身份或所有权差异。
- `control_rod_drive` 不接受红石调节；红石只通过 `reactor_instrument_port` 触发 SCRAM。
- 仪表端口高电平持续 SCRAM：插入所有可移动控制棒并锁定滑块；低电平恢复 SCRAM 前保存的目标深度。
- 卡死控制棒保持实际插入比例，不能被滑块或 SCRAM 强行改变。
- 结构只在形成、拆除或组件变化时重扫，不每 tick 全量扫描。

**GameTest：** 成型、运行、正常停堆、滑块同步、SCRAM 高低电平、控制棒卡死、冷却剂端口和存档重载。

### P1.2-REFUEL-01：换料和钢板维修事务

**目标：** 实现燃料列顶部换料端口的人工/动力机械臂换料及钢板维修。

**必须实现：**

- 目标列必须满足核心文档规定的停热/控制棒条件后才能换料或维修。
- 右键目标燃料列顶部 `reactor_refueling_port` 使用 1 个 `alloy_steel_plate`，仅修复该列，恢复 `0.25 / internalHeight`。
- 被维修燃料列在维修前必须停止放热；不满足条件时不消耗物品、不改变 NBT。
- 控制棒列使用同一钢板右键 `control_rod_drive` 修复；卡死解除必须以完整度恢复为前提，并遵守核心文档状态机。
- 维修不补燃料、不改变燃料组件耐久、不回退融毁进度。
- 机械臂、玩家交互和失败路径必须原子化，不能吞物品或部分写入。

**GameTest：** 成功维修、低完整度边界、列仍放热时拒绝、空手拒绝、物品不足拒绝、满完整度拒绝、机械臂事务失败回滚。

### P1.2-REFUEL-02：工程师护目镜信息

**目标：** 看向燃料列顶部换料端口时显示该列燃料组件剩余耐久、完整度/损坏度和当前发热量。

**必须实现：**

- 护目镜只读显示，服务端值权威，客户端不自行扫描反应堆或推导热量。
- 组件剩余耐久来自服务端燃料组件状态；完整度来自唯一的 `fuelColumnIntegrity`；损坏度为 `1 - integrity`；发热量为已结算列级 HU/t。
- 无护目镜、端口无效、结构未成型或列为空时不给出误导性的详细数值。
- 观察信息不能打开 GUI、改变换料许可、改变端口库存或修改反应堆状态。

**验收：** 人工检查目标端口绑定、耐久/完整度/发热量随 tick 变化、空列、非目标方块和未佩戴护目镜行为；测试同步和服务端权限边界。

### P1.2-MAINT-01：停机重组成型和拆除融毁

**目标：** 实现安全重置条件以及运行中/融毁中拆除组件的不可逆事故行为。

**完全停机条件：** 无有效裂变产热和燃料消耗、余热已进入安全区、没有运行中或暂停中的融毁倒计时。仅 SCRAM、仅插入控制棒或仅暂停倒计时均不满足条件。

**必须实现：**

- 完全停机后重新成型，永久清空核心 NBT：燃料组件、冷/热冷却剂、控制棒深度、逐列缓存热量、燃料/控制棒完整度和融毁进度；不返还物品。
- 运行、融毁倒计时或暂停融毁倒计时期间拆除任意组件，立即将倒计时置零并执行融毁动作，喷出热复合冷却剂和高放射废物。
- SCRAM 成功、补回组件或重新成型不能回退已经发生的融毁动作。

**GameTest：** 覆盖三种禁止拆除状态、完全停机重置、余热未安全拒绝重置、拆除后即时产物、重装不回退进度。

### P1.0-PONDER-01：P1 内容 Ponder

**目标：** 为已实现的多方块结构、单方块设备、端口/管道和主动使用物品提供 Create 风格思索入口。

**范围：** 只覆盖当前已实现并注册的 P1 内容；未实现对象不得用假场景占位。

**必须覆盖：** 5×5×5 成型、多个冷却剂端口、控制棒滑块、SCRAM、换料、护目镜信息、损伤/传播/融毁、钢板维修和安全拆除规则。

**边界：** Ponder 只能展示，不得直接修改服务端燃料、控制棒、冷却剂、完整度或融毁状态；中文和英文文本都必须可本地化。

## 5. 每个任务的完成定义

任务只有同时满足以下条件才能交项目经理验收：

- 代码、资源、测试和注册项全部在任务范围内。
- 无核心文档或活动计划变更。
- 无 Git 历史变更、无删除用户文件、无无关格式化。
- `.\gradlew.bat test` 通过；涉及资源时运行数据生成/资源契约测试。
- 涉及游戏世界交互时运行 `.\gradlew.bat runGameTestServer`，并提交通过的测试名称。
- 需要客户端交互时完成 `runClient` 人工验收；需要服务端生命周期时完成 `runServer` 或等价集成验证。
- `git diff --check` 通过；只读报告改动文件列表和差异摘要。
- 提供已知缺陷、未实现项、存档/NBT兼容影响和下一步建议。
