## 6. 任务 P0-NUM-01：P1 数值原型

### 6.1 目标

建立不依赖 Minecraft 世界的纯 Java、确定性、可注入参数的反应堆数值模型，验证发热、燃耗、冷却剂转化、完整度损伤、实时热量传播、控制棒卡死和融毁倒计时是否形成可控闭环。

数值原型是 P1 实现的测试基准，不是最终平衡。原型必须允许替换参数，不得把默认值散落在测试或方块实体中。

### 6.2 推荐模型边界

使用逐列输入和上一轮快照计算，所有列的结果与遍历顺序无关。至少包含：

- `fuelColumnIntegrity`：`0～1`，每个燃料列独立保存。
- `controlRodColumnIntegrity`：`0～1`，每个控制棒列独立保存。
- `fuelRemaining`/`remainingFuelFraction`：燃料组件剩余燃料；与完整度分离。
- `controlRodDepth`：`0～1`，完全插入和完全抽出必须在模型中有明确约定。
- `cachedHeat`/余热：燃料列停止产热后仍可用于本 tick 实时传播。
- `meltdownProgress`/`meltdownCountdown`：只允许前进或暂停，不能因冷却和 SCRAM 回退。
- 四向邻接关系：只包含水平北、南、东、西，不含对角线和上下方向。

推荐的 P0 计算顺序：

```text
1. 读取上一 tick 的完整快照和结构缓存。
2. 根据控制棒深度、局部相邻燃料和配置倍率，求有界的 heatEquivalent/burnEquivalent。
3. 根据完整度计算 damageMultiplier；完整度归零列的发热和燃耗为 0。
4. 计算每列 generatedHeat、plannedBurn、coolantRemovedHeat 和 netHeatLoad。
5. 按 netHeatLoad 更新燃料列完整度；冷却足够时不损伤，即使处于超频。
6. 用传播前快照读取失效燃料列余热，四向传播；目标列冷却可把传播热量降为 0。
7. 更新控制棒列完整度；归零则卡死并停止继续传播。
8. 按当前传播热量覆盖比例建立或暂停融毁倒计时；不保存传播标记。
9. 结算燃料消耗、冷/热冷却剂账本和下一 tick 缓存热量。
```

### 6.3 P0 默认参数

以下值是验证用原型默认值。除维修物品消耗和修复量外，所有值都必须通过参数对象注入；最终 P1 再映射到服务器配置。

| 参数 | 默认值 | P0 验证要求 |
| :--- | :--- | :--- |
| `baseHeatPerFuel` | `1.0 HU/t` | 单个有效燃料棒方块的基础发热 |
| `burnHoursPerBlock` | `3 h` | 满功率、无超频、有效高度 1 的燃料寿命；不得和另一燃耗权威重复 |
| `coolantAbsorptionHuPerMb` | `1.0 HU/mB` | 冷却剂吸热换算 |
| `coolantMaxFlowPerPort` | `100 mB/t` | 单个冷端/热端流量上限 |
| `coolantTotalFlowCap` | `200 mB/t` | 单座反应堆总流量上限 |
| `fuelColumnDamageHeatThreshold` | `0.25 HU/t` | 净残余热量超过阈值才损伤 |
| `fuelColumnDamageRate` | `0.00125 / (tick·HU/t)` | 超过阈值的线性损伤速率 |
| `fuelColumnDamageTransferRate` | `0.25` | 失效列向四向邻列传播的热量比例 |
| `controlRodColumnFailureThreshold` | `0.0` | 控制棒列归零即卡死 |

固定、不进入配置的维修规则：

```text
每次维修消耗 1 个合金钢板；目标燃料列必须停止放热；
完整度恢复量 = 0.25 / internalHeight；最后一次封顶到 1.0；
维修不补燃料、不清除缓存热量、不解除控制棒卡死、不回退融毁进度。
```

### 6.4 必须验证的数值性质

#### 燃料、控制和热量

- 全部控制棒插入时，反应速率和发热达到设计的最低运行状态；正常停堆不消耗燃料。
- 控制棒深度对本列及相邻列的作用单调且有界；控制棒列卡死后保持卡死前实际插入比例。
- 直接相邻燃料列可以形成超频反馈；中空列和控制棒列切断燃料反馈簇。
- 完整度越低，仍有效列的发热和燃耗按相同比例提高；完整度归零时二者均为 0。
- `internalHeight=1`、满功率、无超频时，燃料寿命为 3 小时；高度变化线性放大总热量、燃耗和库存，不重复叠加倍率。
- 发热、燃耗、完整度和缓存热量不能为负数、NaN 或无穷大。

#### 冷却剂转化

```text
convertedCoolant = min(
    availableColdCoolant,
    availableHeat / coolantAbsorptionHuPerMb,
    availableHotOutputCapacity,
    perPortAndTotalFlowCaps
)
removedHeat = convertedCoolant × coolantAbsorptionHuPerMb
netHeatLoad = max(0, generatedHeat - removedHeat)
```

- 多端口只提高可用流量直到单端口/全堆上限，不直接增加发热或燃耗。
- 冷却剂不足不会降低燃料消耗来掩盖危险；输出堵塞不能无声删除热量。
- 冷却充分时 `netHeatLoad=0`，超频列完整度不下降。
- 输入、输出和热量账本均守恒；重复连接和重复遍历不重复结算。

#### 损伤、传播和融毁

- 损伤只由每列有效净残余热负荷累计产生；不得使用全堆平均损伤。
- 失效燃料列停止产热/燃耗，但其缓存/余热按传播前快照向四向邻列传递。
- 目标列冷却完全带走传播热量时，传播伤害为零；控制棒列不把传播热量继续向外扩散。
- 不保存传播标记；改变列遍历顺序、区块加载顺序和存档重载顺序，结果必须一致。
- 当前传播热量覆盖 `20%` 有效燃料列时建立倒计时；控制棒列不计入分母。
- SCRAM 或有效冷却可以暂停融毁倒计时，但任何操作不能回退进度；全列完整度恢复到 `1.0` 才能重置。

### 6.5 数值场景矩阵

每个场景都要输出最终状态、逐 tick 关键值和通过/失败结论。建议至少运行以下场景：

| 场景 | 输入 | 预期检查 |
| :--- | :--- | :--- |
| N-01 | 空堆/无燃料 | 发热、燃耗、损伤、传播和倒计时均为 0 |
| N-02 | 单列、满燃料、全插入 | 无意外超频；寿命与 3 小时锚点一致 |
| N-03 | 单列、逐步抽棒 | 控制深度、发热、燃耗单调且有界 |
| N-04 | 两列相邻与隔一列 | 相邻产生反馈，隔开的燃料不直接反馈 |
| N-05 | 多列连续燃料簇 | 反馈迭代收敛且不因遍历顺序改变 |
| N-06 | 完整度 `1.0/0.75/0.5/0.25/0` | 发热/燃耗同比反馈，归零停止 |
| N-07 | 冷却 `0/50/100/200 mB/t` | 流量受端口/总上限控制，充分冷却不损伤 |
| N-08 | 失效燃料列邻接燃料列 | 只沿四向传播，传播受目标冷却阻断 |
| N-09 | 失效燃料列邻接控制棒列 | 控制棒完整度下降，归零卡死且不继续外传 |
| N-10 | 传播热量覆盖 `19%/20%/21%` | 仅达到阈值时建立倒计时，控制棒列不计分母 |
| N-11 | SCRAM/有效冷却/危险恢复 | 倒计时暂停但进度不回退，危险恢复后继续 |
| N-12 | 全部燃料列与控制棒列维修 | 只有全列完整度为 1 才重置融毁状态 |
| N-13 | 高度 `1/3/5` 参数化列 | 总热、燃耗、寿命按高度线性缩放；维修量按 `0.25/internalHeight` |
| N-14 | 随机列顺序和存档快照重载 | 结果确定、状态不丢失、不产生传播标记 |

### 6.6 P0-NUM-01 通过门槛

数值原型只有在以下条件全部满足后才能通过：

1. JUnit 5 测试通过，关键性质有自动断言而不是人工看日志。
2. 所有默认参数可注入，维修消耗/修复量固定规则没有配置旁路。
3. 热量、冷却剂、燃料和融毁进度没有守恒破坏、负值或非确定性。
4. 3 小时燃料寿命、20% 融毁阈值、控制棒卡死、四向传播、冷却阻断和全列修复重置均有场景证据。
5. 参数扫描结果以表格或 CSV 写入 `build/reports/p0/`，列出安全区、危险区和会立刻融毁的极端区间。
6. 如果推荐默认值导致 P1 无法启动、无法停堆、冷却永远追不上或损伤永远不发生，任务必须标记为“数值阻塞”，不得自行改写核心文档。

## 7. P0-API-01 与 P0-NUM-01 的联合验证

API 探针和数值原型完成后，用一个最小测试适配层证明两者能连接，但不实现完整 P1：

- API 层只负责提供假燃料列、假端口、假控制输入和 tick 调用。
- 数值层只接受纯数据快照和参数，不引用方块坐标、玩家、Create 方块实体或世界对象。
- 适配层验证服务端 tick 调用一次、端口流量结算一次、NBT 序列化一次，不能因为多个端口或多个事件重复执行模拟。
- 将一轮模拟结果写入核心 NBT 的测试替身，再读取并继续下一 tick，结果必须与连续运行一致。
- 客户端滑块/护目镜只读取同步快照；客户端不得成为数值模型的第二个权威来源。

联合验证不通过时，P1-REACTOR、P1-REFUEL、P1-REFUEL-02 和 P1-MAINT 全部保持待执行。

## 8. 测试和命令清单

### 纯逻辑

- `.\gradlew.bat test`
- JUnit 5 覆盖公式、边界、参数校验、快照序列化和随机场景重放。

### Minecraft/NeoForge

- `.\gradlew.bat runGameTestServer`
- 需要客户端滑块或护目镜时：`.\gradlew.bat runClient`
- 需要生命周期/专用服务端时：`.\gradlew.bat runServer`
- 涉及注册/资源时：`.\gradlew.bat runData`，并检查生成结果是否误改核心文档或无关资源。

### 最终检查

- `.\gradlew.bat build`
- `git diff --check`
- `git status --short --branch`
- 只读审查 `git diff --name-only`，确保没有越界文件。

GameTest 结构模板必须与测试注解命名空间完全一致，放在 `src/test/resources/data/create_nuclear_industry/structures/`；缺失模板、未注册测试类或超时都算失败，不得只保留 JUnit 通过结果。

## 9. 交付物与完成定义

### P0-API-01 交付物

- API 结论表：每项 API 的入口、调用侧、线程、同步、失败行为、版本限制和替代方案。
- 可重复运行的编译/最小运行探针或 GameTest。
- 客户端滑块、护目镜和服务端事务的人工验收记录。
- `build/reports/p0/api/` 下的日志/截图索引/运行命令记录。

### P0-NUM-01 交付物

- 纯 Java 参数对象和数值原型测试；不把其误注册为正式内容。
- JUnit 场景矩阵和确定性/守恒/单调性断言。
- `build/reports/p0/numeric/` 下的参数表、CSV、边界结论和默认值建议。
- 一份“可进入 P1 / 数值阻塞”的结论，注明仍需用户或项目经理决策的事项。

### 共同完成定义

- 没有修改核心文档、活动计划和既有用户文件。
- 没有 Git 历史变更；开发者没有 commit、分支、回退或合并。
- 所有修改文件都属于任务范围，并能在交付报告中逐一解释。
- `test`、必要的 `runGameTestServer`/`runClient`、`build` 和 `git diff --check` 结果完整。
- 已知缺陷、不可行 API、参数风险、注册/存档影响和下一任务建议齐全。
- 项目经理审查后，才决定是否保留探针代码、更新核心文档和提交版本。

## 11. 推荐派发顺序

```text
P0-BASE-01 基线与测试环境只读检查
        ↓
P0-API-01 Create/NeoForge API 探针
        ├─ P0-API-REVIEW API 结论与适配方案评审
```
