# 项目经理执行计划：2026-08-17 启动与首发垂直切片

**负责人：** 项目经理（Codex）
**产品决策人：** 用户
**执行者：** 经授权的 agent/开发者；只实现已确认任务
**当前模式：** 只讨论玩法、技术路线和可行性；项目经理不编写功能代码

## 1. 接单前必须遵守的规则

- agent/开发者不得执行 `commit`、`reset`、`revert`、`checkout`、`switch`、`branch`、`merge`、`rebase`、`cherry-pick`、`clean` 或删除/覆盖用户文件等 Git/工作区管理操作。
- 只有项目经理和用户可以提交、回退、创建/切换分支、合并或处理冲突。开发者可以读取 `status`、`diff` 和日志来定位问题，但不得改变 Git 历史。
- agent/开发者不得擅自修改五份核心设计文档、路线图或活动计划来追认代码行为；需求变更先回报项目经理。
- 项目经理不写功能代码，不替开发者补实现；项目经理负责需求澄清、文档落地、任务验收、证据审计和 Git 版本管理。
- 用户已有的未提交修改默认属于用户工作。没有明确授权时，不覆盖、不回退、不混入别人的提交。

## 2. 任务交接模板

每个任务必须明确以下字段：

| 字段 | 要求 |
| :--- | :--- |
| 任务 ID | 例如 `P1.2-SIM-01` |
| 目标 | 玩家问题或技术问题，而不是模糊的“完成系统” |
| 范围 | 允许修改的代码、资源和测试目录 |
| 不在范围 | 明确禁止顺手新增的内容 |
| 前置依赖 | 依赖哪个文档决定、接口或任务出口 |
| 失败用例 | 至少列出拒绝路径、边界值或守恒失败 |
| 自动化验证 | JUnit、资源契约、GameTest、构建命令 |
| 游戏内验收 | 手动步骤和预期结果 |
| 完成定义 | 代码、资源、测试、文档和交接证据必须齐全 |

开发者交付时必须回报：实际改动文件、运行过的命令及结果、人工验收结果、已知缺陷、未实现项、存档/注册兼容影响和建议下一任务。未提供证据的任务保持“待验收”。

## 3. 首批任务清单

### PM-00 文档与仓库基线

- **状态：** 本计划创建后进入待验收
- **范围：** `docs/` 文档索引、路线图、归档说明、当前 Git 状态审计
- **不在范围：** 删除 `NewMod/project.md`、修改用户未提交内容、编写功能代码
- **出口：** 路线图和活动计划可访问；旧稿被标为非权威；构建/测试基线可复现

### P0-API-01 Create 6.0.10 最小可行性核查

- **目标：** 证明热源注册、Create 应力输出、普通流体能力和动力机械臂交互的真实 API 入口。
- **前置：** 当前 Gradle 版本基线。
- **交付：** API 备忘录或最小探针；说明服务端/客户端边界、可用回调、数值类型和限制。
- **失败用例：** 不存在统一热源 API、应力容量精度不足、机械臂不能提供受控物品端点时，必须提出适配层或调整方案，不得静默替换玩法。
- **验收：** `test`/`build` 通过，关键结论有源码或最小运行证据。

### P1.1-DATA-01 燃料组件状态合同

- **目标：** 建立 `fresh_fuel_assembly`、`cooled_spent_fuel_assembly` 和 `fuel_assembly` 数据组件。
- **前置：** `content-catalog.md` 与 `recipes.md` 的身份约束。
- **必须覆盖：** 原版耐久语义、剩余燃料比例、燃料身份、`decayHeatHu` 预留字段、format 版本、序列化往返和耗尽转冷却态。
- **禁止：** 保存组件温度/完整度；用煤炭或木炭作为运行时别名；注册可放置控制棒柱方块。
- **验收：** 纯单元测试 + 资源契约；创造模式可获得仅算开发入口，不算 P1.3 生存完成。

### P1.1-FLUID-01 复合冷却剂身份合同

- **目标：** 注册 `compound_coolant` 和 `hot_compound_coolant`，定义容器、流体属性、热/冷状态转换边界。
- **必须覆盖：** 标准 NeoForge 流体能力、热端不能被普通桶徒手抽取、换热转换不复制流体、运行时状态不使用熔岩/水别名。
- **验收：** 注册/资源/标签测试，流体能力最小运行验证；数量和加工时间留待平衡门。

### P1.2-SIM-01 纯 Java 反应堆模拟核心

- **目标：** 按已批准的局部控制文档实现四向邻接、平均控制棒深度、超频反馈、燃耗、余热和边界配置校验。
- **前置：** 燃料数据合同；局部控制文档中的冲突规则由用户确认。
- **必须覆盖：** 空控制棒、多个控制棒平均、反馈不跨空列/控制棒列、非线性增长、有界收敛、倍率上限、燃料耗尽后的局部重算、燃耗不受热量上限回退保护。
- **禁止：** 每个燃料方块单独注册组件；把世界坐标、Create 方块实体或应力网络写入核心模型。
- **验收：** JUnit 5 确定性测试；无 Minecraft 启动依赖。

### P1.2-REACTOR-01 固定结构实验反应堆

- **目标：** 接入仪表接口权威状态、结构缓存、控制棒驱动器、SCRAM 和护目镜只读信息。
- **前置：** `P1.2-SIM-01`。
- **必须覆盖：** 仪表接口唯一、控制端口可选、冷/热端口要求、控制棒独立服务端深度、余热不停 tick、结构变化才重扫。
- **验收：** NeoForge GameTest + 手动结构搭建/拆除；运行中失效结构不能丢失或复制燃料。

### P1.2-REFUEL-01 单列换料端口

- **目标：** 实现燃料列正上方无 GUI 端口的人工/动力机械臂受控访问。
- **前置：** `P1.1-DATA-01`、`P1.2-REACTOR-01`。
- **必须覆盖：** 目标列所有生效控制棒完全插入且裂变产热为零，或燃料已耗尽；先取出再装入；原子失败回滚；其他列继续运行；普通漏斗/通用管道拒绝。
- **验收：** GameTest 覆盖成功、拒绝、并发/状态变化时不吞物品和不重置堆状态。

### P1.3-RECIPES-01 最小生存材料链

- **目标：** 先完成实验堆必需的铅/锡/铀原料、标签、钢材、冷却剂和燃料制造链。
- **前置：** `P1.1-DATA-01`、`P1.1-FLUID-01`、`recipes.md`。
- **必须覆盖：** 原版/Create 可达、标签输入、Create 工序优先、铀尾矿和容器守恒、屏蔽装配边界。
- **禁止：** 在数量/时间/应力未冻结前自行宣称平衡；悄悄增加文档没有的副产物或替代输入。
- **验收：** 数据生成/资源契约/配方守恒测试 + 一次完整生存生产线人工验收。

### P1.4-THERMAL-01 三模式核换热器

- **目标：** 实现热复合冷却剂供热、超临界蒸汽降级供热、普通 `steam` 冷凝三种互斥模式。
- **前置：** `P0-API-01`、`P1.1-FLUID-01`。
- **必须覆盖：** 核热品质与普通热品质分离、受热负载检查、冷源标签、无冷源/出水阻塞安全停机、余热窗口、普通 steam 唯一 ID。
- **验收：** 纯账本测试 + Create 运行探针 + 游戏内流体测试；禁止伪造蒸汽引擎流体能力。

### P1.4-TURBINE-01 固定尺寸汽轮机与 SU 输出

- **目标：** 以固定尺寸完成超临界蒸汽消耗、转速惯性、普通 steam 排汽和多主轴不重复分配应力。
- **前置：** `P1.4-THERMAL-01` 和 `P0-API-01`。
- **必须覆盖：** 无负载超速、旁通/制动、排汽受阻、输出端容量分配、应力数值边界。
- **验收：** 模拟/集成测试、至少一次手动黑启动和安全停机；标准商用规模先由 P0 原型冻结，不能直接硬编码文档目标。

### P1.4-VERTICAL-01 首发垂直切片验收

- **目标：** 串起最小生存生产、启动、运行、停堆、冷凝回水、冷却乏燃料和封存。
- **前置：** P1.2、P1.3、P1.4 全部出口。
- **验收：** 新玩家按 Ponder/仪表在 30 分钟内完成实验堆启动和安全停机；至少两类故障有不同反馈和处置；连续运行、存档重载和四套机组性能基线有记录。

## 4. 测试分层

依据 Minecraft 模组测试规范，任务必须按层提供证据：

1. **JUnit 纯逻辑：** 反应堆模拟、流体/燃料账本、配置范围、序列化往返。
2. **资源契约：** 注册 ID、翻译、模型、标签、掉落、配方输入和数据生成输出。
3. **NeoForge GameTest：** 结构扫描、方块交互、端口事务、服务端权威、运行 tick 行为。
4. **集成运行：** `./gradlew runGameTestServer`、必要时 `runClient`/`runServer`。
5. **人工验收：** 生存材料链、Ponder 启动、故障预警、停机/维修和存档重载。

`.\gradlew.bat test` 和 `.\gradlew.bat build` 是当前基线命令。当前基线已通过，但不能替代 GameTest 或生存验收。

## 5. Git 与版本管理流程

- 任务实现期间不允许 agent/开发者改变 Git 历史；只提交工作区文件和验证报告。
- 项目经理接收后先记录 `git status --short --branch`、目标分支和基线提交，再审查 diff 与测试。
- 提交按合同粒度拆分，建议格式：`docs: ...`、`feat: ...`、`test: ...`、`fix: ...`、`chore: ...`。
- 提交前必须：目标测试通过、`git diff --check` 通过、注册/存档影响已说明、文档状态已同步、无意外文件。
- 回退优先使用可追踪的 `git revert`；不使用破坏性 reset 覆盖用户工作。合并前工作区必须干净，且明确哪些用户修改已保留。
- 若工作区同时含用户修改和开发者交付，项目经理只暂存已验收的明确文件；不使用全量 `git add .`。

## 6. 当前执行结论

首个可交给开发者的技术任务不是“实现完整核电站”，而是 `P0-API-01` 和 `P1.1-DATA-01`。在这两个合同稳定前，任何大规模反应堆/锅炉代码都视为高风险返工。项目经理下一步负责收集用户对局部控制冲突、首发垂直切片边界和 Create API 适配取舍的确认，再更新受影响的五份设计文档并派发任务。
