# 反应堆管理员：GUI、连续换料与核热值班设计

2026-10-14。用户要求管理员拥有专用GUI，部分燃料列耗尽不能导致整堆停机，并补充任职烈焰人消耗反应堆热量维持燃烧、冷启动需要一个燃料。用户随后明确“可以，开始施工吧”，批准本稿及推荐参数，按[实施卡03](../plans/2026-10-14-reactor-administrator-gui-03.md)在原管理员候选接续实现。原01/01R未因此登记人工通过，02应力闭环仍未开工。

## 1. 界面入口与组织

推荐Create风格的“总览／堆芯／保护”三页，普通空手右击任职燃烧室打开。持有效燃料仍走原补料入口；扳手与机械臂保持原交互。设置迁入GUI，原燃烧室四个世界控件撤下；护目镜只显示状态、实际发热和主要异常。打开或关闭界面不改变管理员运行状态，界面不暂停反应堆结算。

总览承接日常操作，堆芯用于定位问题，保护页用于检查停堆与复位条件。单页可展开方案较紧凑，但需要频繁滚动，不作为推荐。初版采用约312×224 GUI单位的面板布局，并在实际最小缩放窗口验证；状态同时使用文字与图标，不能只依赖颜色。

| 页面 | 信息与交互 |
| --- | --- |
| 总览 | 机组尺寸、停堆/建立联锁/运行/预警/故障保持状态；运行模式与对应设置；目标、实际及当前可达发热HU/t；目标与平均实际插深；冷液/热液/空余共享容量条；可用、枯竭、空燃料列统计；管理员供能来源、外部燃料剩余燃烧时间、核热自耗和净可供热量。 |

总览先接当前手动与恒定功率；02实施后加入应力余量模式、应力表绑定信息、容量/负载、当前/目标余量和最低运行发热，不提前展示未启用模式。

## 2. 设置与安全操作

模式选择和数值输入只形成编辑草稿，按“应用”才由服务端确认；启动是独立操作。运行模式切换仍经过原安全交接，不能通过GUI绕过全插入基准和联锁。数值支持直接输入及步进按钮，大功率不用连续滚轮操作。

所有页面固定保留“停堆”按钮，立即走原安全停堆入口；故障复位需要单独确认，并显示实际健康稳定进度。关界面或Esc丢弃未提交编辑，不撤销已经确认的运行设置。没有有效供能时仍可查看信息和停堆，启动与复位按钮显示不满足条件的原因。

GUI复用仪表唯一权威、接口设定与原控制服务；不复制第二份反应堆状态。服务端验证玩家可达性、实际燃烧室/接口实例、结构代际和设置版本；多玩家旧提交不能覆盖新设置。一次设置应用原子校验并确认，避免多个字段逐个提交造成中途切换或旧戳失效。客户端显示过期或绑定失效时撤销可操作状态，不强载区块。

GUI只向当前查看者同步显示投影：打开时完整布局，后续只更新变化的状态；以低频刷新显示数值，故障/绑定失效即时通知。显示平滑沿用原40tick，不延迟每tick保护；不借客户端L1/L2美术数据决定运行。具体菜单/协议文件和预算在设计冻结后的实施卡列出。

## 3. 部分燃料耗尽与自动换料

当前Controller将任意已装枯竭组件判为fuel_lost，Service前后tick还会因可用列数量下降撤权；三处属于同一过严燃料规则，应统一按新语义修订。

- 有至少一列可用燃料时，部分列耗尽或为空不因燃料原因停堆。显示枯竭/空列并重新计算功率曲线；目标超过新可达上限时报告上限，按原步长调节，不虚增热量。
- 自动换入新组件后重新预测可达范围和下一tick冷却需求，按原限速追踪目标；不会仅因有效列数量变化撤销运行许可、转故障或要求复位。
- 可用燃料列归零时才因堆芯缺燃料保持停堆。补料恢复健康条件后仍需原人工复位/启动，不能自行提棒。
- 未受控的有效燃料、损伤、卡死、冷却不足、失联与事故保护独立保持。枯竭列的真实余热仍进入账本与保护，不因其已无法裂变而删除。

界面分别使用“堆芯燃料全部耗尽”和“管理员供能中断”等原因，避免把反应堆燃料与烈焰人值班供能混为同一种缺料。

## 4. 核热维持燃烧

### 玩家行为

1. 完全冷态无可用堆内热量、也无剩余外部燃烧时间时，正常投喂一个能点燃Create燃烧室的燃料。沿用原燃料持续时间及容器返还，不固定要求煤，也不增加第二种启动物品。
2. 启动反应堆后，热量足以支付维护成本即自动改为核热值班，不需要持续供燃料；界面显示“反应堆供热”。只有已经任职当前反应堆的燃烧室可以取热。
3. 停堆后可继续消耗真实余热维持值班，便于监测与处理停堆状态。没有可用热量时可退回剩余外部燃烧时间；两种供能都没有则熄火、运行许可归零并保持停堆。
4. 核热恢复或重新补料不清除故障保持，也不自动启动。管理员有火焰不代表反应堆正在运行，状态栏分别显示两者。

核热维持普通燃烧等级KINDLED，不因反应堆规模或功率获得超级加热。默认耗热按现行一个普通燃烧室的热级成本核算：**1 HU/t**，对应当前换热器huPerLevel=1的一个热级。管理员新增正、有限、可配置的`burnerMaintenanceHuPerTick`，已批准默认1；热级标尺改变时应一起校准，不用未经建模的煤热值推估。

普通外部燃料在核热值班期间不再重复扣燃烧时间，保留剩余时间作启动/备用；失去核热后恢复原计时。特殊燃料燃烧期间采用原外部供能、按原时长消耗，不同时扣核热维护费，也不能借核热冻结其超级加热时长；结束后有已支付核热才恢复普通核热值班。未任职燃烧室与原创造燃烧室的原生供能规则保持。

### 真实热账本

维护支付来自同一反应堆本tick新生裂变热量加既存真实余热，在冷却剂结算前扣除；先支付新生热量，余额再从既存余热按各列余额比例扣除，逐列移除总量恰等于支付量。未足额支付时不生成核热值班资格，也不部分扣热；不透支、不另造“温度”或无限热缓存。已经转入热冷却液的能量不再重复取用。

热支出必须在原正式核tick事务中一次结算、一次提交；燃料端口提交/核tick失败不能先发供热资格。供热资格仅覆盖已经付款的极短tick窗口，处理反应堆与燃烧室BE先后顺序，不能从旧显示包、卸载前状态或墙钟时间续燃。结构/实例/代际失效即时撤销核热关联，既有外部燃料回到普通规则。

维护热移除不得冒充冷却剂实际结算量、冷却回路畅通或事故有效冷却；原冷却启动条件、库存保护、逐列损伤与融毁判定仍使用各自真实依据。小额维护不是缺冷时继续运行的许可。

毛裂变发热、管理员自耗、实际冷却移热及热账本保持分别记账。GUI的“净新生供热”为max(0，毛新生热量－本tick已支付维护热量)，真实余热及其维护支出单列显示；恒功率目标仍是毛裂变HU/t，不悄悄改成净输出目标。

## 5. 与最低功率、停堆的关系

02的最低运行发热仍是毛HU/t，健康空载保持正运行功率。现在需要同时覆盖管理员自耗和后端最低供热需求；当设定不大于维护成本时，GUI明确提示没有新生热量供给后端。

已批准02工程默认最低毛发热从原1调整为**维护成本＋1 HU/t**，在当前默认维护1时为2 HU/t；该值只为留出正净热量，仍不保证满足具体汽轮机门槛或大锅炉启动需求。目标应力余量20%、PI算法、库存保护与限速含义保持。安全故障、玩家停堆与急停依然可以覆盖最低功率并全插棒。本批只登记此后续默认规则，不实施02。

全部堆芯燃料耗尽即使尚有余热让烈焰人燃烧，也不能继续运行许可；控制棒全插入后核热值班可持续到真实余热耗尽。没有冷却条件时，即使外部燃料或余热充足也保持停堆。
